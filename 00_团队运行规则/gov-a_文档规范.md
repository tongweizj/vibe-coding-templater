## 〇、迭代版本划分与产品版本（v3.0 核心）

### 0.1 为什么分迭代版本

项目从「**把站建起来**」进入「**把站运营好**」，是**性质的变化**，不是里程碑的延续：

| 维度 | v1.0 建站主线 | v2.0 运营优化 |
|---|---|---|
| 核心目标 | 从零打通「采集→发布」全链路 | 在跑通的基础上提效、降门槛、做运营 |
| 需求来源 | 建站必需（没有它站跑不起来） | 运营痛点（有了它运营更省力） |
| 完成定义 | 「**能自动跑通**」 | 「**运营者能轻松操控**」 |
| 典型需求 | 采集、打标、聚类、翻译、发布、监控 | admin 操作台、发布监控、部署告警 |
| 形态 | 搭骨架 | 加肌肉、打磨手感 |

因为性质不同，两者**不应混在同一份需求清单里滚动**——否则「建站必需的 20 项」会淹没「运营优化的 10 项」，优先级判断失真。

> 📌 上表以「建站 / 运营」二分说明迭代版本制的由来；**当前已细化为四个迭代版本**（v1.0 建站 / v2.0 运营优化 / v2.1 上线 / v3.0 深度运营），完整分界见 §0.2、版本表见 §0.3。

### 0.2 分界线（每段各自一条，不可移动）

> **分界线不再全局唯一，而是「每段各自一条」**——因为各段文档数量不同，"迭代版本切换点"的编号自然不同。
>
> 📌 **四个迭代版本（2026-09-28 项目主管拍板，v4.13 正式化）**：**v1.0 建站** → **v2.0 运营优化** → **v2.1 上线** → **v3.0 深度运营**。判据统一为「**内容所属产品版本**」。

| 段 | v1.0（建站） | v2.0（运营优化） | v2.1（上线） | v3.0（深度运营） | 本段分界 |
|---|---|---|---|---|---|
| `01` 项目管理 | `pm-01a` - `pm-01b` | `pm-02a`/`pm-02b` | **`v2.1_上线/` 专目录**（`pm-03a`/`pm-03b`/`pm-03c`） | — | `01f` |
| `02` 产品需求 | `v1.0_需求清单` + 全局文档 `02a` | **`prd01c`** + `v2.0_需求清单` + `prd02c` | — | **`prd02a`/`prd02d`/`prd02e`** + `v3.0_需求清单` + `FR-P4`/`P5`/`P6`/`P8` + `FR-D2` 人工档 + `FR-D7` | **内容所属版本**（全局 `02<字母>` 不属版本；`prd01x`/`prd02x` **为默认前缀，内容可跨版本**——`prd01c` 内容属监控后台落 v2.0；`prd02a`/`prd02d`/`prd02e` 内容属深度运营落 v3.0；`prd02b` 内容属上线落 v2.1_上线） |
| `03` 开发文档 | `03a` - `03f` | **`03g` 起**（admin 手动发布与否决为 v2.0 首份设计） | — | — | **`03g`** |
| `00` / `04` | 不分迭代版本（整段同层） | — | — | — | — |

> **`02` 段特殊**：自 v4.2 起 `02` 段编号格式为 `prd<版本><字母>`（见 §2.2），**产品版本号已内嵌在编号里**，因此 02 段的迭代版本不再靠分界编号判定，直接看 `prd01x`/`prd02x` 前缀即可。**但前缀仅为历史标识**——若某文档内容在后续版本迭代中归属变化（如 `prd01c` 内容属监控后台、随 v1.0 收窄下放 v2.0），**以「内容所属版本」为准归档**，前缀不改。

> **"v2.0 首份文档"的判定锚点**：`02_产品需求/v2.0/prd01c_采集监控.md`（采集监控需求，内容属监控后台 v2.0）。**"v3.0 首份文档"锚点** = `02_产品需求/v2.0/prd02a_admin手动操作.md`（admin 操作台，内容属深度运营 v3.0）。

**每条分界线都是一次性判定**：文件一旦归档到 `v1.0/` 或 `v2.0/`，后续不再移动。判断某文档属于哪个迭代版本，**`02` 段看 `prd` 版本号、他段看所在段的分界线**（不是看全局某个编号）。

> ⚠️ **注意**：编号在各段内**独立**（`02x` 与 `03x` 互不干扰）。因此 `prd02a` 属 v2.0，而 `03d` 仍属 v1.0——**同名不同段，迭代版本可以不同**。

### 0.3 产品版本号（新增）

在原有「各文档独立 `vX.Y`」之上，增加**产品版本**层，形成双层版本：

| 产品版本 | 对应迭代版本 | 内容 | 允许的里程碑 |
|---|---|---|---|
| **v1.0** | v1.0 建站主线 | 从零到「全链路自动跑通」：M1 采集 → M2 智能处理 → M3 自动发布 → M4a/M4b 监控 | M1 - M4b |
| **v2.0** | v2.0 运营优化 | 「能看 + 能扩」：M4c 发布监控（监控后台 `FR-M1`~`FR-M6`）→ M6 多地域（温哥华 `prd02c`） | M4c、M6（多地域） |
| **v2.1** | **v2.1 上线**（2026-09-26 新增，项目主管立项） | 把流水线搬上 Ubuntu 家庭服务器：M5 生产上线（部署 / Cron 落地 / 网络代理 / 告警 / 上线检查清单） | M5 |
| **v3.0** | **v3.0 深度运营**（2026-09-28 项目主管拍板正式化） | 「能全权操控」：M4d admin 操作台 → M6 平台增强（话题级 `/` 频道标签配置 `/` 内容增强）+ 发布人工档（`FR-D2` `manual`/`semi_auto`）+ 人工否决（`FR-D7`） | M4d、M6（配置类） |

**版本规则**：

- 产品版本**只在迭代版本边界处升位**（`v1.0 → v2.0 → v2.1 → v3.0`）——**每次升位都发生在一次迭代版本切换**：v1.0→v2.0（跑通转运营）、v2.0→v2.1（运营转上线）、v2.1→v3.0（上线转深度运营）。截至本文（v4.15），四个版本均已立项。
- 产品版本与文档版本**互不干扰**：文档仍是自己的 `vX.Y`（如 `pm-01b` 可以既是「产品 v1.0 期文档」又自身 `v1.3`）。
- 每份文档头部在「版本」字段后可选标注所属迭代版本，格式见 §四。

## 一、团队与文档归属

我们是一个 **vibe coding 团队，共 4 个角色**。文档按「谁负责」分段，每个编号段对应一个负责人。

| 角色 | 定位 | 负责文档段 | 核心产出 |
|---|---|---|---|
| **项目主管**（Max，人类） | 方向拍板、方案裁决、验收签收、git push | —（参与所有） | 拍板记录、验收结论 |
| **项目经理** | 团队运转与进度把控 | `01` 项目管理 | 待办、计划、进度快照、阻塞清单 |
| **产品经理** | 定义「做什么、验收什么」 | `02` 产品需求 | 需求文档（FR + 验收）、数据模型 |
| **开发主管** | 定义「怎么做、做出来」 | `03` 开发文档 | 设计文档、代码、测试 |
| **开发主管** | 面向使用者的操作手册 | `04` 使用说明 | 操作说明（工具操作 `04a` + 概念/链路解释 `04b`） |

**全员参与**：`00` 团队运行规则 — 团队所有人必须遵守，任何角色发现规则不适用都可发起修订。

> `00` / `01` / `02` / `03` / `04` 五个 **index 文件移入本段目录**（如 `01_项目管理/pm_项目管理.md`），作为各段导航入口；具体子文档在**本段目录内**按迭代版本下沉到 `v1.0/` 或 `v2.0/` 子目录。

**根目录仅一个文件**：

| 类型 | 文件 | 说明 |
|---|---|---|
| **总览入口** | `DASHBOARD.md` | 项目总 Dashboard（**不编号**）：聚合当前迭代/看板/需求/里程碑/阻塞/待拍板 + 快速导航。**聚合视图**，非事实源 |

> 注意：**所有 index 文件均已不在根目录**，分别移入各自段目录（`00_团队运行规则/gov_团队运行规则.md`、`01_项目管理/pm_项目管理.md`、`02_产品需求/02_产品需求.md`、`03_开发文档/03_开发文档.md`），`04_使用说明.md` 则在专目录 `04_manual/` 内。

**目录划分原则**：

| 目录 | 收纳 | 划分维度 |
|---|---|---|
| `00_团队运行规则/` | `00` 段全部文档（index + gov-a/gov-b），**不分迭代版本** | **按段**（全员规则跨迭代版本统一） |
| `01_项目管理/` | `01` 段文档，段内分 `v1.0/`（`pm-01a`-`pm-01b`）、`v2.0/`（`pm-02a`/`pm-02b`）与 **`v2.1_上线/`**（v2.1 上线专目录，`pm-03a`/`pm-03b`/`pm-03c`） | **先按段，段内按迭代版本** |
| `02_产品需求/` | `02` 段文档：**全局文档 `02a` 在段根**；版本需求分 `v1.0/`（`prd01c`）与 `v2.0/`（`prd02a`+） | **先按段，段内按迭代版本** |
| `03_开发文档/` | `03` 段文档，段内分 `v1.0/`（`03a`-`03f`）与 `v2.0/`（`03g`+） | **先按段，段内按迭代版本** |
| `04_manual/` | `04` 段全部子文档（`04a`/`04b`/…） | **按分类**（使用说明独立成目录，不随迭代版本流动） |

> **为何从「按迭代版本」改为「先按段、段内按迭代版本」**：原两迭代版本大目录（`ph01_build/` / `ph02_ops/`）把**不同负责人**的文档混在同一层——如原 `ph02_ops/` 里既有产品经理的需求又有开发主管的设计，检索时需先辨认段号。改为段目录后，**「谁的文档在哪个目录」一眼可见**，且段内迭代版本分层保留了 v1.0/v2.0 的区分度。
>
> **为何 `00` 段不再分迭代版本**：团队运行规则（规范/流程/职责）是**跨迭代版本的稳定约定**，不随产品版本演进，故整段单层。

> **为何 `04` 独立成目录**：使用说明是**面向运营者的操作手册**，性质上「跨迭代版本、持续维护」——它不随某个里程碑诞生，而是随功能上线不断增补（如 M4d 上线后 `04a` 要加写操作章节）。因此不按迭代版本归档，单独立目录管理。

### 2.2 命名格式

**通用命名格式**：`<段位缩写>-[<VV>]<序号>_<中文主题>.md`

> **⚠️ v4.16（Max 2026-09-28 拍板）**：段位由 2 位数字改为**英文缩写**（段位即命名空间）：`gov`=00 / `pm`=01 / `prd`=02 / `dev`=03 / `man`=04。完整语法、命名空间登记、机检规则详见 **`gov-c_文档编码规则.md`（v1.2 生效中）**——本节保留历史约定叙述，两者冲突处以 `gov-c` 为准。
> **段 index 特例（A1）**：各段 index **不编号**，形态 `<段位>_<主题>.md`（`gov_团队运行规则.md` / `pm_项目管理.md`）。
> **`01` 段**：子文档为**版本内嵌** `pm-<VV><序号>_<中文主题>.md`——`pm-01a`/`pm-01b`/`pm-02a`/`pm-02b` 已改名（2026-09-28 项目经理执行）；`02`/`03`/`04` 段改名待各负责人（gov-c §十 L2）。

| 形式 | 含义 | 说明 |
|---|---|---|
| `[0N]` | **分类 index 文件**（N = 0,1,2,3,4） | 该分类的入口索引，必须写清：**本分类所有文件 + 每个文件的用途和目的**。**存放在本段目录内**（`04` 段 index `04_使用说明.md` 在专目录 `04_manual/` 内，与子文档同目录）。 |
| `[0NA]` | **分类下的子文件**（A = a,b,c…） | 具体文档。`01`/`02`/`03` 段按迭代版本下沉到本段目录的 `v1.0/` 或 `v2.0/`；`00` 段与 `04` 段不分迭代版本（`00` 直放段目录、`04` 进 `04_manual/`） |
| `DASHBOARD.md` | **项目总 Dashboard**（**不编号**） | 根目录的唯一总览入口，聚合视图。**不占编号**（它不是某个分类 index，而是全项目总览）。 |

**`02` 段（产品需求）命名格式（v4.3 起）**：分**四类**——**跨版本全局文档** 用 `02<字母>`；**版本内需求** 用 `prd<版本号><字母>`；**已映射 FR 的需求文档** 用 `FR-<编码>_<功能名>需求文档`（v4.6，见 §2.6）；**版本级需求清单** 用 `v<版本号>_需求清单`（v4.7）。

`02` 段文档分三类性质，命名因而不同：

| 类别 | 命名格式 | 落点 | 含义 |
|---|---|---|---|
| **全局文档**（跨版本） | `02<字母>_<中文主题>.md` | **段目录根** `02_产品需求/` | 不属于任何产品版本、描述**整个产品结构与总纲**的文档。如 `02a_需求总览.md`（产品结构总纲，贯穿 v1.0/v2.0） |
| **版本需求**（迭代版本内） | `prd<版本号><字母>_<中文主题>.md` | 段内 `v1.0/` 或 `v2.0/` | 归属某个产品版本、**未与单一 FR 映射**的具体需求。`prd01x`→`v1.0/`，`prd02x`→`v2.0/` |
| **FR 需求文档**（v4.6） | `FR-<编码>_<功能名>需求文档.md` | 段内 `v1.0/` 或 `v2.0/` | **已与 `02a` 的功能编码一一映射**的需求文档。编码同其开发文档（见 §2.6） |
| **版本级需求清单**（v4.7） | `v<版本号>_需求清单.md` | 段内 `v1.0/` / `v2.0/` / `v3.0/` | **跨该版本全部 FR** 的范围界定/选型汇总（如 `v1.0_需求清单.md`）。不占 `02<字母>` / `prd<版本><字母>` 位 |

**版本需求**格式细节：`prd` 前缀 + 产品版本号 + 版本内排序字母：

| 形式 | 含义 | 说明 |
|---|---|---|

| `02_产品需求/*`、`03_开发文档/*` | ❌ **禁止**——用**文档编号互指**（如「见 `prd01c_采集监控.md` §FR2」） |
| `04_manual/*` | ❌ **禁止** |

**为何**：里程碑是**产品排期**的概念（第几个交付节点），不是**功能**的概念。需求/开发文档回答「这个功能做什么/怎么做」，用**文档编号**互指最稳定——即使里程碑重排，文档编号也不受影响。反之，若需求文档写死「M3」，一旦排期调整就会全线失效。

**替代写法**：原「见 M3 自动发布需求」→ 改为「见 `FR-D1_定时发布开发文档.md`」（文档编号互指）。

### 2.6 功能编码命名（FR 命名，v4.6 新增）

**规则一句话**：**凡已与 `02a_需求总览` 的功能编码（FR）一一映射的文档，文件名以该 FR 编码为准**；需求与开发**共用同一 FR 码**，仅靠**后缀**区分文档性质。

**FR 编码来源**：以 `02a_需求总览.md` §2 的模块化功能需求编号为唯一权威。现有四组：

| 模块码 | 模块 | 编号形态 | 来源 |
|---|---|---|---|
| `FR-C` | 采集 | `FR-C1`、`FR-C2`… | `02a` §2.1 |
| `FR-P` | 智能处理 | `FR-P1`、`FR-P2`… | `02a` §2.2 |
| `FR-D` | 发布 | `FR-D1`、`FR-D2`… | `02a` §2.3 |
| `FR-M` | 监控后台 | `FR-M1`、`FR-M2`… | `02a` §2.4 |

**命名格式**：

| 文档性质 | 命名格式 | 示例 |
|---|---|---|
| **需求文档** | `FR-<编码>_<功能名>需求文档.md` | `FR-D1_定时发布需求文档.md` |
| **开发文档** | `FR-<编码>_<功能名>开发文档.md` | `FR-D1_定时发布开发文档.md` |
| **模块级需求文档**（覆盖整个模块多条 FR） | `FR-<模块>_<模块名>需求文档.md` | `FR-D_发布需求文档.md` |
| **模块级开发文档**（覆盖整个模块多条 FR） | `FR-<模块>_<模块名>开发文档.md` | `FR-D_发布开发文档.md` |

**要点**：

1. **编码唯一映射**：文件名里的 FR 码必须能**一一对应** `02a` 里的功能需求条目；一条需求对应一份文档（或一份模块级文档覆盖该模块的连续多条，用模块码 `FR-<模块>`）。
2. **后缀区分性质**：同一 FR 码下，**`...需求文档.md`** 归 `02` 段（产品经理）、**`...开发文档.md`** 归 `03` 段（开发主管）——**编码相同、段与后缀不同**。
3. **适用范围**：**仅「已映射」的文档**改用 FR 命名；**未与任何 FR 映射**的文档（如全局总纲 `02a_需求总览.md`、总体设计 `03a_总体设计.md`、数据模型 `03b_文章模型.md`、跨模块流程 `03d_文章发布流程.md` 等）**保留原编号**（`02<字母>` / `prd…` / `03<字母>`）。
4. **不占原编号序列**：FR 命名文档**不占** `02<字母>` / `03<字母>` 的字母位——它们与字母编号是**两套并行**的命名空间（FR 码锚定需求，字母编号锚定段内顺序）。
5. **模块名与功能名**：`<功能名>` 与其映射的 `02a` 功能需求名保持一致（中文，主题清晰），不夹带任务编号。

> **例**：`FR-D1_定时发布开发文档.md`（对应 `02a` §2.3 `FR-D1` 定时发布）；若改为覆盖整个发布模块，则用模块码 → `FR-D_发布开发文档.md`。

每份子文档头部固定带一行元信息（三段式开发文档模板起点）：

```

```

| 字段 | 取值 | 必填 |
|---|---|---|
| 版本 | 文档自身版本，如 `v1.0` | ✅ |
| 日期 | `YYYY-MM-DD` | ✅ |
| 状态 | 如「待评审 / 已定稿 / 已拍板 / 生效中」 | ✅ |
| 迭代版本 | `v1.0 建站` 或 `v2.0 运营` | ✅ |

| 关联文档 | 引用的其他文档编号（**用相对路径**，见 §五） | ⭕ 推荐 |

> ⚠️ **头部只放元信息，不放变更摘要**（v4.15 明确）：变更历史**一律**记在「变更记录」表（文末 §N，或该段的 index），**不在头部另写「vX.Y 变更」段落**——否则同一事实写两遍、易出现版本号重复与顺序错乱。头部如需指引，只写一行「变更历史见文末 §N 变更记录」。

## 五、跨目录引用规则（重要）

目录分层为「**根 → 段目录 → 迭代版本子目录**」三级，跨层引用必须使用**正确相对路径**：

| 引用场景 | 写法 | 示例 |
|---|---|---|
| **同段同迭代版本**（如 v1.0 → v1.0） | 同目录，直接文件名 | `[03b_文章模型.md](03b_文章模型.md)` |
| **同段跨迭代版本**（如 v1.0 → v2.0） | `../v2.0/<文件名>` | `[prd02a_admin手动操作.md](../v2.0/prd02a_admin手动操作.md)` |
| **跨段**（如 `02` 段 → `03` 段） | `../../03_开发文档/<迭代版本>/<文件名>` | `[03a_总体设计.md](../../03_开发文档/v1.0/03a_总体设计.md)` |
| **段内子文档 → 本段 index** | `../<index文件名>` | `[02_产品需求.md](../02_产品需求.md)` |
| **index → 本段子文档** | `<迭代版本>/<文件名>` | `[v1.0/03a_总体设计.md](../03_开发文档/v1.0/03a_总体设计.md)` |
| **index → 他段 index** | `../<段目录>/<index文件名>` | `[pm_项目管理.md](../01_项目管理/pm_项目管理.md)` |
| **任意文档 → `DASHBOARD.md`** | 逐级 `../` 回到根 | `[DASHBOARD.md](../../DASHBOARD.md)` |
| **任意文档 → `04_manual`** | 逐级 `../` 到根再进 `04_manual/` | `[04a_admin使用说明.md](../../04_manual/04a_admin使用说明.md)` |
| **`04_manual` → 各段文档** | `../<段目录>/<迭代版本>/<文件名>` | `[03a_总体设计.md](../03_开发文档/v1.0/03a_总体设计.md)` |
| **`04_使用说明.md` → 同目录子文档** | 直接文件名 | `[04a_admin使用说明.md](04a_admin使用说明.md)` |
| **`04_使用说明.md` → 各段文档** | `../<段目录>/<迭代版本>/<文件名>` | `[03a_总体设计.md](../03_开发文档/v1.0/03a_总体设计.md)` |
| 文档内**文字提及**编号 | 只写编号，不带路径 | 「见 `FR-D1_定时发布开发文档.md` §4」 |

> 上表「示例」列均为**写法示范**（用反引号包裹，非可点击链接）；实际撰写时按对应场景替换为真实路径。
>
> **相对路径心算法**：先确定「当前文件在哪个目录」，再数「目标文件在第几层」——根是第 0 层，段目录是第 1 层，迭代版本子目录是第 2 层。同层用文件名，上一层用 `../`，下两层用 `<段目录>/<迭代版本>/`。

> **约定**：正文中用 backtick 提及编号时**不写路径**（可读性优先）；Markdown 链接**必须写正确相对路径**（可用性优先）。**建议**：当一份文档内大量引用他段编号时，可直接用「文件标题文字」或编号 + 文件名，减少长路径噪声。

## 六、需求文档的开发方式（三段式）

一个功能从「提出」到「落地」，走**三段式**，每段产出对应文档、由对应角色负责：

```
阶段一：产品需求（02 段）  →  阶段二：开发文档（03 段）  →  阶段三：开发实现
   「做什么、验收什么」        「怎么做、有哪些决策点」       「代码 + 测试」
     负责人：产品经理            负责人：开发主管            负责人：开发主管
```

> 这里的「阶段一/二/三」是**单个功能的三段式**，与 §〇 的 **迭代版本（v1.0/v2.0/v2.1/v3.0）** 是两回事，勿混淆。

### 6.1 阶段一：产品需求文档（What / 验收）

**标准结构**：

```
# <功能名> — 需求文档
> 版本 · 日期 · 状态 · 迭代版本 · 负责人 · 关联文档

1. 背景与目标          # 为什么做、达成什么
2. 现状梳理            # 当前代码/数据状态（含遗留问题）
3. 功能需求（FR）      # 编号 FR1/FR2/...，每项含验收
4. 接口约定            # 如有外部对接
5. 数据流              # 端到端流转
6. 非功能需求（NFR）   # 幂等/安全/可恢复/可观测等
7. 验收标准            # 可验证的通过条件
8. 风险与待定          # 待拍板清单，逐项给建议
```

**关键要求**：

- 功能需求用 `FR` 编号，可追溯；每个 FR 附「验收」。
- 待拍板项**显式列出**并给建议，不隐藏假设。
- 需求文档**不写实现细节**（不写代码、不写模块划分）。

### 6.2 阶段二：开发文档 / 实现级设计（How / 决策）

**标准结构**：

```
# <功能名> — 开发文档（实现级设计）
> 版本 · 日期 · 状态 · 迭代版本 · 定位（引用上游需求）

0. 拍板记录            # 已定决策汇总
1. 目标与现状          # 本轮缺口
2. 设计子问题清单      # 每个子问题：决策 + 状态（✅已定/⬜待定）
3. 总体设计            # 数据流 + 模块划分
4. 接口契约            # 字段映射、请求/响应
5. 状态与字段变更      # 数据模型改动
6. 错误处理矩阵        # 各失败场景行为
7. 代码改动清单        # 文件级改动
8. 测试方案            # 用例 + 跑法
9. 验收标准
10. 不在本轮范围       # 明确边界
11. 待确认清单         # 依赖外部（如 site 侧）
```

**关键要求**：

- **先列设计子问题清单**再动手（Max 的「先设计后实现」）。
- 每个子问题给出决策 + 状态，未定的标 `⬜ 待定`。
- 接口契约、错误矩阵是重灾区，必须显式写清。

### 6.3 阶段三：开发实现（Code / 测试）

- 按开发文档的「代码改动清单」落地。
- 测试方案落地为 `test/test_*.py`，跑绿 + 真实联调。
- 完成后回写 `pm-01b_kanban.md` 状态、更新 `pm-01a_项目计划.md`。

3. 交叉引用用**新编号 + 正确相对路径**（§五）。
4. **新增/删除子文件必须同步更新**：① 所属 `[0N]` index 文件；② 本规范 §2.4 完整目录索引。
5. 需求/设计完成一个里程碑，同步 `pm-01a_项目计划.md` 状态与 `pm-01b_kanban.md`。

7. **编号重排属结构性变更**：需同时更新本规范 §2.4、所有相关 index、以及全部交叉引用。
8. **`DASHBOARD.md` 每轮随 `pm-01a`/`pm-01b` 同步刷新**：项目经理在每轮收尾时更新其七区块；它**不产生新事实**，只镜像源文档（冲突以源文档为准）。
