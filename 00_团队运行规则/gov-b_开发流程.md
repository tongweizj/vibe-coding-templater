## 〇、团队现实与四条原则（v2.0 新增，凌驾于后文细节）

**本团队是一个 vibe coding 团队**：1 位人类项目主管（Max）+ 3 个 AI 角色会话（项目经理 / 产品经理 / 开发主管，各占一个对话窗口 + agent）。三个会话**记忆不互通**，共享同一份 git 工作树和文档目录。由此推导四条硬约束：

| # | 原则 | 内容 |
|---|---|---|
| 1 | **文档即接口** | 会话之间看不到彼此的对话，跨角色协作**只通过本目录的文档落盘**。任务卡必须**自包含**（背景 + 依据文档编号 + 验收标准），不假设执行会话知道任何对话内容。会话内讨论出的结论若未落盘，等于没发生。 |
| 2 | **看板即路由** | 派活不靠传话：`pm-01b_kanban.md` §0.5「本轮看板」是**唯一任务派发通道**。项目经理把自包含任务卡写入看板（负责人 / 轮次 / 做什么 / 怎么做 / 验收 / 引用文档）；Max 每轮推进时只需在对应窗口说「按启动指令开工」，角色读板、认领自己名下 ⬜ 的最高优先级卡——**Max 指定谁开工，看板决定干什么**。 |
| 3 | **串行轮转** | 三个会话共享同一个 git 工作树和同一批文档，并发必冲突。**同一时间只激活一个角色会话**：上一个角色 commit 完、文档回写完，Max 再启动下一个。 |
| 4 | **职责即文件域** | 角色不越界修改他人文档，文档编号即文件域边界：**项目经理**只写 `01` 全段（`pm-01a`/`pm-01b` 等）；**产品经理**只写 `gov-a` + `02` 全段；**开发主管**只写 `03` 全段 + `04` 全段（`04_manual/`）。发现上游文档有问题，在对方文档对应处加「⚠️ 反馈：<问题>」行交回，不直接改。详见 `gov-a_文档规范.md` §三。 |

## 一、团队角色与职责

团队 = **1 位人类项目主管 + 3 个 AI 角色会话**：项目主管、项目经理、产品经理、开发主管（后三者为独立对话窗口中的 agent，非真人）。

| 角色 | 核心职责 | 主要产出 | 不做什么 |
|---|---|---|---|
| **项目主管**（Max） | ① 方向与优先级拍板 ② 方案级决策裁决（需求方案 A/B、设计待定项）③ 验收签收 ④ git push（SSH 密钥沙箱限制，仅主管可推）⑤ 外部协调（site 侧确认、商家/内容资源） | 拍板记录、pushed commits、验收结论 | 不直接写代码和需求/设计文档 |
| **项目经理** | ① 从待办清单取任务、拆解、排序、分派 ② 进度跟踪、风险与阻塞清单维护 ③ 组织每轮开发循环、把控出口条件 ④ 文档状态同步监督（`pm-01b` / `pm-01a`）⑤ 向项目主管汇报进度与风险 | `01` 全段（`pm-01b_kanban.md` 状态维护、`pm-01a_项目计划.md`） | 不拍板方案级决策；不代写需求/设计正文 |
| **产品经理** | ① 需求文档（阶段一：FR 编号 + 验收 + 待拍板清单）② 文档规范维护（`gov-a`） | `gov-a` + `02` 全段 | 不写实现细节（模块划分、代码、接口契约）；**不写 `04` 段使用说明** |
| **开发主管** | ① 设计文档（阶段二：设计子问题清单 + 接口契约 + 错误矩阵）② 数据模型文档（`03b` 文章模型）③ 代码实现与测试（阶段三）④ git commit ⑤ 技术债与实现备注记录 ⑥ 使用说明（`04` 全段：`04a` 工具操作 + `04b` 概念/链路解释） | `03` 全段、`04_manual/` 全段（`04_使用说明.md`/`04a`/`04b`）、`app/` 代码 + `test/test_*.py`、commits | 不跳过设计子问题清单直接写码；不自行变更需求范围 |

**一句话分工**：产品管「做什么、验收什么」，开发管「怎么做、做出来」，项目经理管「按什么顺序做、做到哪了」，项目主管管「要不要做、做得对不对」。

## 二、配合方式：开发轮次循环

### 2.1 轻重两级轮次

vibe coding 的效率优势靠「小任务不设仪式」来保留：

| 轮次 | 适用 | 流程 |
|---|---|---|
| **标准轮次** | 新功能、跨模块改动（如 A2.1 翻译方案 B、A7.1 联调） | 六步全走（§2.2），走三段式文档（02x 需求 → 04x 设计 → 实现） |
| **快速轮次** | 小修、配置、文案、单点修复（如 D7 停用词过滤） | 跳过独立需求/设计文档：任务卡自包含（改什么 + 验收 + 边界）→ 开发主管直接实现 → 测试全绿 → 回写 pm-01b。涉及方案取舍的仍升级 L2 拍板 |

### 2.2 标准轮次六步闭环

每轮任务对应 `gov-a_文档规范.md` 的三段式，扩展为六个步骤：

```
① 取任务 → ② 需求 → ③ 设计 → ④ 实现+测试 → ⑤ 回写+commit → ⑥ 验收关闭
  项目经理   产品经理   开发主管     开发主管        开发主管→PM    主管+PM
```

| 步骤 | 负责 | 动作 | 出口条件 |
|---|---|---|---|
| ① 任务入板 | 项目经理 | 从 `pm-01b` 按优先级（P0→P1→P2）取任务，把**自包含任务卡**写入 `pm-01b` §0.5 本轮看板（负责人角色、轮次、做什么、怎么做、验收、引用文档编号）——执行会话看不到任何对话，卡是它的全部输入 | 卡自包含，负责人明确 |
| ② 需求确认 | 产品经理 | 已有需求文档（`02x`）的直接引用；没有的补写需求文档（FR + 验收 + 待拍板清单） | 待拍板项全部由项目主管拍板 |
| ③ 设计确认 | 开发主管 | **先列设计子问题清单**（Q1/Q2…），产出 `03x` 开发文档；未定项标 ⬜ 并升级项目主管 | 拍板记录齐，无阻塞开发的 ⬜ |
| ④ 开发实现 | 开发主管 | 按「代码改动清单」落地；测试方案 → `test/test_*.py` 全绿；需联调的按联调步骤跑 | 测试全绿 + 验收标准可逐项核验 |
| ⑤ 回写提交 | 开发主管 | **只更新看板卡**（`pm-01b` §0.5）：置 🔍待验收 + 附可复核证据；git commit。pm-01b 分区行与 `pm-01a` 里程碑**不在此步动**（01 段是项目经理文件域），由步骤⑥验收时统一回写 | 卡证据齐全可复核 |
| ⑥ 验收关闭 | 项目主管 + 项目经理 | 项目经理对照验收标准核验 🔍 卡（亲测可复核项：跑测试、抽查代码），通过置 ✅ 并**统一回写 pm-01b 分区与 pm-01a 里程碑**；✅ 必须附**可复核证据**（测试命令+结果、实测数据、commit 号）；主管抽查 + 关键节点签收，不必逐项人审；主管 push | 卡置 ✅，pm-01a/pm-01b 同步 |

### 卡片排版规范（v4.2 定版，项目主管 2026-09-28 拍板）

适用于 `01_项目管理/` 各阶段看板（`pm-01b`/`pm-02a_kanban` 等）。存量 ✅ 存档卡**不回改**，新立卡一律按此执行：

1. **分区顺序**（在途优先展示）：

   ```
   ## 🔶 进行中   ← 会话领卡开发中
   ## ⬜ 待办     ← 已立卡未派活
   ## ✅ 完成     ← PM 验收通过（含证据链），沉底归档
   ```

2. **卡片 = 独立章节 + 段落式字段**：每卡一个 `### K<n> · <任务名>（<需求编号>）` 章节，字段用 `####` 小节标题 + 正文段落，**不用表格**（横向/竖向均弃用）：

   ```
   ### K2 · T5 发布监控页（FR-M5 / M4c）

   #### 需求来源
   <FR 编号 + 任务清单来源 + 收编脉络>

   #### 做什么
   <改什么，分 ①②… 点列>

   #### 设计约束
   <技术边界与硬约束>

   #### 前置
   <依赖项；无则写「无」>

   #### 验收标准
   <①②③④ 逐条可核验>

   #### 状态
   ⬜ 待办 / 🔶 进行中（谁） / 🔍 待验收 / ✅ 完成

   #### 交付证据
   <commit 号 + 测试输出，执行角色填写>
   ```

3. **自包含不变**（原则 1）：任何会话领卡即可开工，卡是执行会话的全部输入；卡号与需求编号双向引用。

### 关键纪律

1. **先设计后实现**：设计子问题清单未拍板完，不动代码（项目主管工作习惯，gov-a §4.2 同款要求）。
2. **单一事实源**：任务状态只看 `pm-01b_kanban.md`（原 `01d_待办清单.md`），里程碑状态只看 `pm-01a_项目计划.md`（原 `01e_实施计划.md`），其余文档不再另行记进度。
3. **测试全绿才算完成**：不凭「应该没问题」标 ✅；每个 ✅ 必须附证据（测试名 / 实测数据 / commit 号）。
4. **commit / push 分离**：开发主管 commit，项目主管手动 push。
5. **文档编号合规**：所有新文档按 `gov-a_文档规范.md` 编码规则命名，存放 `52sask-news-pipeline-doc/`。

### 2.3 看板认领协议与统一启动指令

**看板** = `pm-01b_kanban.md`（原 `01d_待办清单.md`）§0.5「本轮看板」，唯一的任务派发与状态通道。

**卡状态流转**：

```
⬜ 待办 ──认领──► 🔶 进行中 ──完成+证据──► 🔍 待验收 ──PM核验──► ✅ 完成
                      │
                      └── 依赖不满足/需求不符 ──► 🚫 阻塞（注明原因，交回项目经理）
```

**认领规则**：

1. 角色开工只看看板：找「负责角色 = 自己」且状态 ⬜ 的卡，按优先级取**第一张**。
2. 开工第一件事：把卡状态改为 🔶 并填认领时间——这是占用声明，与串行轮转构成双保险。
3. 名下无 ⬜ 卡 → 回复「名下无待办」并停止，**不得自行找活**。
4. 卡完成后不删除：置 🔍/✅，内容同步回写 pm-01b 对应分区，保留追溯。
5. 卡内容与实际不符（需求变更/依赖不满足）→ 卡置 🚫 注明原因交回项目经理，**不得自行变更卡的范围**。

**统一启动指令**（Max 在对应窗口复制一句话即可拉起角色，免粘贴任务卡）：

| 角色 | 启动指令 |
|---|---|
| 产品经理 / 开发主管 | 「你是 52sask <角色名>。按 `gov-b_开发流程.md` §2.3 启动：先读根目录 `DASHBOARD.md`（项目总览），再读 00 全段 + `01_项目管理/v1.0/pm-01b_kanban.md` §0.5 本轮看板，附带你文件域内的关联文档（**产品经理**：`02_产品需求/`（含 `v1.0/`、`v2.0/`、`v3.0/`）；**开发主管**：`03_开发文档/` 与 `04_manual/`），认领你名下 ⬜ 的最高优先级卡并执行。名下无卡则回复『名下无待办』。」 |

- 项目经理维护阻塞清单（基准表在 `pm-01a_项目计划.md`（原 `01e_实施计划.md`）「阻塞项」），每轮结束刷新。

- 每轮结束向项目主管同步三件事：数据快照（pool 分布）、阻塞变化、下一步计划。
- **会话上下文丢失**（vibe coding 特有）：角色会话随时可能新开/重开——一切状态以文档为准；各角色收尾动作固定为「回写文档 + commit」，未落盘的结论视为不存在。
- **并发冲突**（vibe coding 特有）：违反串行轮转导致的文件/git 冲突。以 git 实际状态为准，冲突方放弃本地改动、重新读文档对齐后再做。
